MARUS / DWP2 / Crest / Gazebo Sim 水动力学代码对比报告

这份报告基于当前本地源码静态阅读整理，目标是回答四个问题： 这些项目的“水相关计算”各自主要做什么、算法层面有什么不同、哪个更适合你借鉴到自己的代码里，以及对应的大致工作量。

生成时间：2026-05-29　 检查范围：Packages/com.iwin-fins.fins-sim、Packages/com.nwh.dynamicwaterphysics、 Assets/Crest 与 Gazebo Sim 上游源码
MARUS 自研代码 + Crest 采样适配 NWH Dynamic Water Physics 2（DWP2） Crest 波面 / 查询 / 动态波 / 流场 Gazebo Sim Buoyancy / Hydrodynamics / BuoyancyEngine

先看结论

一句话总结： 如果你要做的是 Unity 里的开源水动力系统，最值得直接借鉴的代码组合是 MARUS + Crest；如果你要借鉴的是 算法思想，并且目标包含 AUV / ROV 六自由度动力学，最值得吸收的是 gz-sim 的 Fossen 模型； NWH DWP2 的工程实现很成熟，但因为许可不是标准开源协议，不适合直接拷贝到公开仓库。
最适合直接改造

MARUS + Crest

同样是 Unity/C#，而且本项目已经在用 Crest 做水面采样。 MARUS 自己的 BoatPhysics 已经有“网格切水面 + 面片受力”的雏形， Crest 则提供更强的波面、法向、流场查询。

最成熟但不宜直接拷

NWH DWP2

在 Unity 里做浮体/船体水动力，DWP2 的结构比 MARUS 更完整更稳定， 但本地源码头部和 package.json 都明确指向 Unity Asset Store 许可， 不建议直接复制到你的开源项目里。

波面最强

Crest

Crest 的强项是海面本身：波谱、Gerstner、FFT、动态波、流场、碰撞查询。 它不是完整船体水动力求解器，但它是非常好的“水面场”和“水面采样 API”。

AUV/ROV 模型最物理

gz-sim

gz-sim 的 Hydrodynamics 是标准的 6DOF 系数模型路线， 更像控制/机器人仿真中的海洋动力学，而不是游戏里常见的“切水面 + 面片力”。 有标定系数时，它往往更物理；没系数时，则未必更“准”。

2. 各项目算法层面到底怎么做？

2.1 MARUS：两条路线并存，且都依赖 Crest 给水位

路线 A Buoyancy.cs：体素浮力
  • 先把物体 collider 按 slicesPerAxis 切成体素点，凹网格时还会做 PointIsInsideMeshCollider() 判定。
  • 每个体素分一份平均的阿基米德浮力 localArchimedesForce。
  • 每帧调用 WaterHeightSampler.Instance.GetWaterLevel() 取每个体素所在位置的水位。
  • 根据体素没入比例 k，叠加 sqrt(k) * buoyancy 与一个简单局部阻尼 -velocity * drag * mass。
  • 核心问题：这套力是直接在 Update() 里加到刚体上，不是在 FixedUpdate() 里。
路线 B BoatPhysics.cs：三角面片切水面
  • ModifyBoatMesh.GenerateUnderwaterMesh() 每次先把船体三角面片按水线切开，区分完全在水下、完全在水上、部分入水。
  • 完全入水的三角面，直接受力；部分入水的三角面会被切成 1 个或 2 个水下三角面。
  • 受力项分 4 类：静水浮力、粘性阻力、压差阻力、拍水力（slamming）。
  • 水位来自 WaterHeightSampler，而 WaterHeightSampler 本质上只是 Crest 的一个薄包装。
MARUS 当前的关键特点： 自己负责“船体怎么切水面、怎么加力”，但不负责“水面怎么产生”。在当前工程里，水面高度基本依赖 Crest 的 CollisionProvider 查询。

MARUS 三角面片路线的具体受力模型：

  • 静水浮力：BoatPhysicsMath.BuoyancyForce() 用的是 rho * g * depth * area * normal 思路，但最后把 x/z 分量直接置零，也就是说它基本只保留竖向浮力，不充分利用水面斜率和局部法向。
  • 粘性阻力：先把点速度投影到切平面，利用 Reynolds 数算 Cf，再做切向摩擦型阻力。
  • 压差阻力：按面法向与速度方向夹角区分 pressure drag / suction drag，系数通过 DebugPhysics 提供，可调性强，但经验性也很强。
  • 拍水力：通过“原始三角形当前/上一帧淹没面积”和速度差估算，属于比较典型的游戏化 slamming 近似。

我对 MARUS 的判断：

  • 它是一个很好的 开源起点，特别适合你做“自己可控的 Unity 水动力骨架”。
  • 但它目前还是 研究型/原型型实现：体素版太粗糙，面片版更合理，但离成熟工程还差 mesh 预处理、水面法向/流场、统一时序、参数标定工具这些层。

2.2 NWH DWP2：成熟的 Unity 工程化版本，核心仍是“切水面 + 面片受力”

  • 预处理更完整：MeshUtility 会做可选的简化、凸包化、顶点焊接，这会显著改善性能和稳定性。
  • 求解主循环更统一：WaterObject.FixedUpdate() 内统一做水面数据查询、三角形分类、受力计算、力矩汇总和刚体施加。
  • 水面数据更丰富：不仅有高度，还可取法向、流场速度；provider 既可以是平面水，也可以是 raycast，也可以接 Crest。
  • 几何处理更扎实：CalcTri()、OneUnderWater()、TwoUnderWater()、ThreeUnderWater() 把部分入水三角面的切分流程写得更稳。

DWP2 的受力模型和 MARUS 的差异：

  • 浮力项不是简单只往上推，而是允许沿着插值后的水面法向施加。
  • 动态阻力由两部分组成：面法向压力项 + 面切向 skin drag 项。
  • 没有像 MARUS 那样单独做“基于面积变化和加速度”的 slamming 方程，而是用 slamForceCoefficient / suctionForceCoefficient 做进入/离开水面的系数调制。
  • 从工程角度看，它更像“稳定、通用、可扩展的统一解算器”；从物理纯度看，它仍然偏经验型，而不是严格的船舶理论模型。
许可边界非常重要： 本地源码头部明确写着 Licensed under Unity Asset Store Terms of Service， package.json 的 licensesUrl 也指向 Unity Asset Store 条款。 这意味着它 不适合直接拷贝进你的开源仓库。你可以学习结构和思路，但不要照搬源码。

2.3 Crest：重点不是“船体水动力”，而是“海面场 + 采样 API”

  • 波面建模：OceanWaveSpectrum.cs 定义谱能量；ShapeGerstner.cs 用 Gerstner 波；ShapeFFT.cs 用 FFT 波面。
  • 大场景组织：OceanRenderer.cs + 一套 LOD 数据管理器，负责波面级联、动态波、流场、深度缓存等。
  • 碰撞/采样：CollProvider 接口允许查询 位移 / 高度 / 法向 / 表面速度；SamplingHelpers.cs 给了单点 helper；CollProviderBakedFFT.cs 提供 CPU/Job 友好的 baked FFT 查询路径。
  • 交互：LodDataMgrDynWaves 和 SphereWaterInteraction / ObjectWaterInteraction 负责把物体运动反馈到动态波模拟中，形成尾迹、波纹等。

Crest 自带的“浮体”脚本本质是示例，不是完整船体求解器：

  • SimpleFloatingObject.cs：单点或单体近似浮力，配合法向对齐和简化阻力。
  • BoatProbes.cs：多个 probe 点采样水面，然后按点权重加浮力和简单阻力。
  • 这类脚本更适合“快速做出会漂、会随浪”的效果，不适合高保真船体水动力研究。
Crest 最值得你借鉴的，不是浮力脚本本身，而是： 波面生成、法向/位移/表面速度/流场查询接口、动态波交互结构。

2.4 gz-sim：真正偏海洋机器人动力学，不是 Unity 式切水面路线

  • Buoyancy：src/systems/buoyancy 负责按照碰撞体积和体积中心加浮力。
  • Hydrodynamics：src/systems/hydrodynamics 负责 6DOF 系数模型，包括线性阻尼、二次阻尼、附加质量、科氏项、海流。
  • BuoyancyEngine：src/systems/buoyancy_engine 是可变浮力引擎，更像水下滑翔机的机械膀胱/压载舱。

gz-sim Buoyancy 的核心思路：

  • 先从 link 的 collision 几何体里算总体积和体积中心。
  • 均匀浮力模式下，直接按 buoyancy = -fluidDensity * volume * gravity 施加。
  • 分层浮力模式下，会按 Z 方向“流体层”切分几何体，对 box/sphere/cylinder/capsule/ellipsoid/cone 调用 VolumeBelow() / CenterOfVolumeBelow()。
  • 这对水下器或简单水面分层很好用，但它不是网格级的自由液面船体受力求解。

gz-sim Hydrodynamics 的核心思路：

  • 明确采用 Fossen 6DOF 海洋航行器模型。
  • 水动力阻尼是矩阵形式：D(v_r) * v_r，其中 v_r = v - current。
  • 线性和二次阻尼系数通过 SNAME 约定命名的 XML/SDF 参数配置，例如 xU、yVabsV、nR。
  • 支持海流 topic 或环境场表插值。
  • 支持附加质量，并对 DART 的 <fluid_added_mass> 做了额外的 Coriolis 修正。
很关键的一点： tutorials/surface_vehicles.md 里提到了 Surface plugin 和 wavefield， 但在你给出的 gz-sim 源码路径下，我没有找到对应的 src/systems/surface 实现。 也就是说，本次能直接比较到的 gz-sim 水相关代码，主要是 浮力、阻尼、附加质量、海流， 不是“波浪下的表面艇网格级相互作用”。

4. 哪个更加精确？这个问题要按场景拆开看

目标 更优的项目 原因
海面高度 / 法向 / 波形细节 Crest 它本来就是波面系统，FFT / Gerstner / LOD / 动态波这些都在它强项里。
Unity 内表面船体 / 漂浮物的开箱即用完整度 NWH DWP2 它的网格预处理、provider 抽象、统一求解流程和调试能力都比 MARUS 现状更成熟。
表面船体的开源可改造性 MARUS + Crest 同是 Unity/C#、许可宽松、项目结构接近你当前工程，落地成本最低。
AUV / ROV 六自由度动力学物理表达 gz-sim Fossen 6DOF、阻尼矩阵、附加质量、海流修正都比 Unity 游戏式浮力模型更正规。
没有实验系数时的“看起来合理 + 工程稳定” NWH DWP2 它虽然经验化，但在 Unity 场景下通常更稳、更完整。

4.1 我对四者“精度”的具体判断

  • MARUS 体素浮力：精度最低，但实现最简单。
  • MARUS 面片浮力：比体素版合理很多，已经是能继续打磨的基础，但它对水面法向/流场/统一时序的处理还不够成熟。
  • NWH DWP2：在 Unity 游戏/仿真语境里，通常会比 MARUS 当前实现更稳、更完整，也更接近“可长期维护的中间层”。
  • Crest：不是“水动力求解最精确”，而是“水面表示最强”。
  • gz-sim：如果你做的是 AUV/ROV，而且你有可靠的阻尼/附加质量/海流参数，那么它的动力学表达最物理；但如果你想做的是“自由液面上 hull mesh 跟波浪的细致作用”，核心仓库里并没有给你现成的那一套。
所以“哪个更精确”的最终答案是：
波面：Crest 最强。
Unity 表面船体受力：NWH DWP2 现成实现更完整，MARUS 更适合开源二次开发。
AUV/ROV 理论动力学：gz-sim 最物理。

5. 借鉴可行性怎么样？借鉴哪个项目最好？

5.1 直接借代码的可行性

来源 直接借代码到你自己的开源项目 原因 更适合借什么
MARUS 高 Apache 2.0，且语言、引擎、工程上下文都和你现在一致。 三角面切水面框架、力项拆分、Crest 水位采样适配方式
Crest 高 MIT，且最有价值的是海面场和采样接口。 波面、法向/位移/表面速度/流场查询、动态波交互结构
NWH DWP2 低 不是常规开源许可，公开仓库直接复制风险高。 只能借工程思路，不建议借源码文本
gz-sim 中 Apache 2.0 没问题，但它是 C++/Gazebo ECS 体系，移植到 Unity 需要重写。 Fossen 模型、参数命名、阻尼/附加质量/海流框架

5.2 如果只能选“最值得借鉴”的项目

如果你要直接改你现在的 Unity 项目

优先借 MARUS + Crest

  • MARUS 给你现成的开源 Unity 受力代码。
  • Crest 给你更强的水面数据源。
  • 你能最快形成一个“完全开源、完全可控”的自有实现。
如果你要借“理论框架”

优先借 gz-sim

  • 特别适合做 AUV / ROV / 水下机器人。
  • 适合把 6DOF 阻尼、附加质量、海流相对速度这一层补到 Unity 里。
  • 不是照抄，而是“按它的模型重写一份 C# 版本”。
我不建议你把 NWH DWP2 作为主借鉴源做“直接复制式开发”。 最好的用法是：读它、学它、重写它的工程结构和思路，但不要把源码直接搬到一个公开开源项目里。

6. 如果是为了完善你自己的代码，我建议的“最佳算法组合”

最佳实践不是四选一，而是组合： Crest 做海面，MARUS/NWH 风格做表面切水面受力，gz-sim 风格做水下 6DOF 阻尼/附加质量/海流。

建议的目标架构

  • 第 1 层：水面场：用 Crest 提供 height / displacement / normal / surface velocity / flow。
  • 第 2 层：表面船体受力：用三角面切水面求解，而不是纯体素或纯 probe。
  • 第 3 层：水下动力学：对 AUV / ROV 加一个 Fossen 风格的 6DOF 系数层。
  • 第 4 层：多级精度：近处或关键对象用三角面切分；远处或小物体用 probe / 简化浮力。

具体应该借哪些点

你应该借的点 最好来源 为什么
水位 / 法向 / 表面速度 / 流场采样接口 Crest 它就是为这件事设计的，而且接口成熟。
船体按水线切三角面 MARUS / NWH 思路 这是 Unity 里做表面艇 hull-water interaction 的合理中间路线。
网格预处理（简化 / 凸包 / 焊接） NWH 思路 这是 MARUS 目前最缺的一块工程化能力。
6DOF 阻尼 / 附加质量 / 海流相对速度 gz-sim 理论上更规范，特别适合水下航行器。
简单浮体 / 低成本物体的备用方案 Crest 示例 probe 或 simple floating object 很适合做低开销 fallback。

7. 工作量大概怎么样？

阶段 内容 预估工作量 价值
Phase 1 把 MARUS 现有水动力统一到 FixedUpdate()，清理 Buoyancy.cs / BoatPhysics.cs 时序，补参数暴露 2 到 4 天 马上提升稳定性
Phase 2 给 MARUS 面片求解器接入 Crest 法向、表面速度、流场；不再只拿高度 2 到 5 天 浪面跟随、相对水速阻力会明显更合理
Phase 3 补上 NWH 风格的 mesh 预处理：简化、焊点、可选凸化、调试显示 3 到 7 天 性能和鲁棒性提升很大
Phase 4 把 MARUS 的阻力项整理成更清晰的统一模型，必要时吸收 DWP2 的法向压力 + skin drag 组织方式 3 到 7 天 代码结构会更像“长期可维护的系统”
Phase 5 为 AUV / ROV 加一层 gz-sim/Fossen 风格的 6DOF 系数模型 1 到 3 周 水下动力学质量提升最大
Phase 6 统一表面模式和水下模式，加参数标定、可视化和 regression 测试 2 到 5 周 形成真正可复用的自有框架

如果只问“要花多少精力，才能明显比现在好很多”：

  • 最低有效投入：大约 1 周，做时序统一 + Crest 法向/流场接入。
  • 比较扎实的升级：大约 2 到 4 周，把 mesh 预处理和更完整的阻力组织一起补上。
  • 做成一套你自己的、能兼顾表面艇和 AUV 的框架：大约 4 到 8 周。

8. 我给你的实际建议

  1. 不要把 NWH DWP2 当成可直接复制的源码来源。把它当成工程结构参考即可。
  2. 短期内最划算的方案：以 MARUS 的 BoatPhysics 为骨架，直接增强它，而不是另起炉灶。
  3. 第一优先增强项：从 Crest 取 normal / surface velocity / flow，让 MARUS 现在的“只看高度”变成“看完整水面状态”。
  4. 第二优先增强项：借鉴 DWP2 的 mesh 预处理思路，把模拟网格简化、焊点、可选凸化加进去。
  5. 第三优先增强项：对水下航行器，单独加一层 gz-sim/Fossen 风格 6DOF 系数模型，而不是把所有问题都塞进表面浮力面片模型里。
如果你问“借鉴什么项目最好”：
直接落地最好：MARUS + Crest。
算法层最好：gz-sim。
工程结构最好但不适合直接拷：NWH DWP2。
